6 Requirements specification

The following requirements describe the intended application, not completed functionality. Must denotes essential scope, Should denotes useful scope that can be deferred. All requirements are proposed from the final Justification and the reviewed sources; none is labelled as validated by interviews. Teacher needs will be linked using evidence codes after the discussions. Administrator accounts belong to a designated content reviewer; supervisor and committee access to project materials does not automatically grant access to teachers’ personal records.

ID / priorityRequirementAcceptance criteria
FR01 / MustAccount access and rolesA registered teacher can sign in/out. Unauthenticated requests receive 401 and a teacher cannot call administrator operations (403). Passwords are never stored in plaintext.
FR02 / MustInitial assessmentA teacher completes 9 original scenario questions, 3 per module, plus separate confidence prompts. Missing mandatory answers prevent submission and receive a field-level error.
FR03 / MustScores and historyThe server stores answers, score, timestamp and content/rule versions. Confidence is displayed separately. A repeated request with the same idempotency key creates one attempt.
FR04 / MustExplainable recommendationThe lowest-scoring incomplete module is recommended; a tied score uses M1, M2, M3 order. The page names the topic and score behind the choice. With no assessment, show the catalogue without a personalised claim.
FR05 / MustThree learning modulesEach published module contains an objective, competence reference, lesson, example, practice brief and completion rules. Unpublished versions are not visible to teachers.
FR06 / MustPractical submissionA teacher saves a text response and an optional HTTPS resource link, then submits. Empty text is rejected; an invalid link does not silently disappear. Drafts remain editable.
FR07 / MustRubric feedbackAn administrator reviews a submitted task using four 0-2 criteria, gives a comment and chooses accepted or revision needed. A teacher can see only their own feedback.
FR08 / MustProgressThe dashboard distinguishes not started, in progress, awaiting review, revision needed and completed. A module completes only after the required lesson steps and an accepted practice submission.
FR09 / MustContent administrationAn administrator creates/edits drafts and publishes a new version. Existing attempts retain their original question and rubric version; publish does not rewrite history.
FR10 / MustData controlA teacher can obtain their own assessment/submission history and request account deletion. The administrator removes associated personal records under the agreed retention process; deletion is logged without retaining the content.
FR11 / ShouldResume and recoverA saved draft can be reopened after sign-out. A failed save shows an error, preserves visible text and offers retry without showing a false success.
FR12 / ShouldPilot exportAn authorised administrator exports pseudonymised, consented pilot records with task/form version, scores, condition and timestamps. Non-consenting accounts are excluded.

Scoring and module selection

The initial diagnostic uses three original scenario questions for each module, scored 0 or 1. Module score = correct answers / 3. The recommended module is the incomplete module with the lowest score; equal scores follow the fixed order M1, M2, M3. A score below 2/3 is labelled "suggested starting point", not "low competence". Confidence prompts are not part of the numeric score. Teachers can override the order. If every module is completed, the page suggests review instead of inventing a new need. These thresholds are an initial product rule requiring review, not a validated psychometric boundary.

Completion has a separate meaning from improvement: completion records the required activities and an accepted practice submission, whereas improvement requires a comparison of practical performance over time. The application must not infer improvement from time spent, a confidence response or a completed lesson alone.

Main use case and alternatives

UC2-UC5 cover the teacher learning cycle. Preconditions: the teacher is authenticated and three module versions are published. Main flow: answer the diagnostic; submit; read the recommendation; open a module; study; save and submit practice; receive feedback; inspect progress. Alternatives: skip personalisation and browse; resume a draft; correct an invalid link; retry a failed save; revise a returned submission. Postcondition: the saved status reflects the actual completed step, and the teacher can retrieve their own record.
